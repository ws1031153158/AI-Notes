# 检索优化
## 检索结果
### 不准确
基础RAG的检索方式为向量相似度检索（similarity_search，语义检索），例如：  
问题："茅台的市盈率是多少？"  
     ↓ 转成向量  
     ↓ 找最相似的向量  
可能检索到：  
✅ "茅台PE为32倍..."          ← 正确  
❌ "茅台酒口感醇厚..."         ← 语义相似但不相关  
❌ "五粮液市盈率为28倍..."     ← 相关概念但不是茅台  
原因：向量检索只看"语义相似"，不看"是否真正回答了问题"，就像搜索引擎只看关键词匹配，不看内容质量
### 优化方案
#### 调整检索参数
1.调整K值，零成本，较高可能含有噪音，较低则结果不全面。  
2.相似度阈值（with_score），零成本，相似度分数越低越相似，0=完全相同，过滤分数较低的结果，保留相关度高的结果（例如score_threshold设为0.5，只要相似度>0.5的结果）
#### 混合检索
MMR检索（mmr_retriever），最大边际相关性，解决结果重复问题，零成本，平衡检索结果相关性和多样性，例如设置：k=3（返回3个结果）,fetch_k=10（先取10个结果候选）,lambda_mult=0.7（相关性阈值为0.7）
#### Reranker重排序
检索后二次重排，低成本，效果最好，需要召回指定向量检索结果，重新打分排序。  
混合检索通过融合多种检索技术，提升检索的召回效果。而这种方法在应用不同的检索模式时，必须对结果进行整合和标准化处理。标准化是指将数据调整到一致的标准范围或格式，以便于更有效地进行比较、分析和处理。在完成这些步骤后，这些数据将整合并提供给大型模型进行处理。为了实现这一过程，需要引入一个评分系统，这就引入了各种Reranker排序模型。  
1.BGE-reranker：BAAI（北京智源人工智能研究院）模型  
2.COhere Rebank：4k的Context长度、覆盖100+语言、支持多种半结构化数据（如支票、JSON、代码、表格、邮件等）
#### 查询改写
把口语化问题变成专业检索词，消耗Token，其实就是让LLM帮助专业化、精准化用户输入
# RAG 封装
## HTTP接口
1.客户端需要通过HTTP调用  
2.前后端分离，各自独立开发  
3.换前端（Flutter/Web）不需要改后端  
4.通过FastAPI+Pydantic（定义请求+响应格式）
## 输出
1.普通输出ResponseBody返回完整一段内容（string，可以说一个完整的data），流式输出（SSE，Server-Sent Events）Responsebody为多个key（data）-value（string）
# 多Agent
1.单Agent：Prompt太长，容易混乱、分析不够深入。  
2.多Agent：Prompt简洁，专注度高，各自深入分析，最后汇总，质量更高。
## 并行
通常Agent并行不是真正的多线程并行，而是"没有依赖关系的任务，不需要等待彼此"，本质上还是串行的 API 调用，只是调度顺序不同。  
真正的并行需要：多线程 / 多进程 + 同时发出多个 API 请求。  
LLM API 调用的限制：模型并发限制、每个 Agent 调用 API 是独立的 HTTP 请求，通常是利用一个“管理者Agent”来调度，管理者决定先让谁做，但还是串行调用。    
真·并行：用asyncio同时发出多个请求，一般数据获取可以这样，但Agent分析层存在依赖关系的要顺序执行。
## 框架
1.CrewAI：概念最直观：Agent就是"角色"，Task就是"任务"，适合角色分工、流程固定   
2.LangGraph：适合复杂流程、条件分支  
3.AutoGen：需要Agent之间互相讨论、辩论  
4.OpenAI Swarm:需要轻量级Agent转交任务时用
