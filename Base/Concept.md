# LLM
## 本质上做什么
<img width="970" height="226" alt="image" src="https://github.com/user-attachments/assets/e46d6b0f-c899-4930-a335-5b07078d55f8" />

LLM 本质上是一个超级复杂的"下一个词预测器"，它在海量文本上训练，学会了"什么词后面跟什么词最合理"，但因为训练数据足够多，它实现了类似出了理解、推理的能力。  
普通输入法：  "今天天气" → 预测 "不错"  
LLM：        "今天天气" → 预测出一篇天气分析报告  
本质是同一件事，但LLM的参数量是输入法的千万倍  
## Training & Inference
### Training
海量数据调整模型参数，巨量GPU
#### 为什么GPU
大模型训练（比如 GPT、LLaMA、Stable Diffusion）本质是大量矩阵乘法和向量运算（矩阵乘、卷积、加法、激活函数等线性代数密集型任务）  
GPU 天生适合做这种 高度并行的数值计算，而 CPU 更适合做复杂的逻辑控制和少量计算（核心数少，单核性能强）  
因此 GPU 在训练大模型时能比 CPU 提供高几个数量级的吞吐量
### Inference
用训练好的模型处理你的输入，生成输出，调用API或本地运行模型  
## 参数量
7B   = 70亿参数   → 可以本地跑，效果一般  
14B  = 140亿参数  → 本地跑需要好显卡，效果较好  
72B  = 720亿参数  → 本地跑需要多卡，效果很好  
GPT-4 → 参数量未公开，估计超过1万亿  
# Token
模型处理文本的最小单位，影响费用、上下文窗口（ContextWindow）、系统设计（RAG）   

<img width="666" height="158" alt="image" src="https://github.com/user-attachments/assets/6954ee75-8bb5-4f7f-a664-f88bb7f5fe84" />  

不同模型切割方式不一样，每个模型都有自己的"词典"（Tokenizer），切法不同 → Token数量不同 → 完全不通用（词典内容不一样）  
## 生成
收集海量文本 -> 统计哪些字/词组合出现频率最高 -> 生成词典（Vocabulary）
## 使用
推理阶段模型用自己的词典切割，变成向量，处理完成后再用词典转回文字
## 买卖
与流量买卖传输数据的能力（和APP无关）不同，Token是买卖这个模型处理文字的能力，和模型绑定
# Context
## ContextProject
与记忆系统形成共生关系，共同支撑Agent的认知能力。记忆系统作为”信息仓库”，存储历史对话、知识和用户偏好；而上下文工程则扮演”智能调度员”，决定从记忆中检索哪些信息及如何组织呈现给LLM。  
LLM的性能和有效性根本上取决于其接收的上下文。实现了上下文工程的系统一般包含三类基础组件：  
1.上下文检索与生成：涵盖Prompt生成和外部知识获取。  
2.上下文处理：涉及长序列处理、自我完善和结构化信息集成。  
3.上下文管理：关注记忆层次、压缩技术和优化策略。  
## ContextWindow
模型在一次对话中能"看到"的最大Token数量，也就是短期记忆容量，超出这个范围的内容，模型完全不知道存在

# RAG
Retrieval-Augmented Generation，检索增强生成，让AI做"开卷考试"而不是"闭卷考试"，避免幻觉
## Embedding
把文字转换成一串数字（向量），让计算机能计算两段文字的"语义相似度"。  
例如："苹果手机"    →  [0.2, 0.8, 0.1, 0.9, ...]  （1536维数字），"iPhone"      →  [0.21, 0.79, 0.11, 0.88, ...] （1536维数字），"苹果手机" 和 "iPhone" 的向量 → 非常接近  ✅ 语义相似    
语义相似：向量相似度计算（余弦相似度）1.0，越小相似越低，-1 时语义相反
## 使用
建库阶段（离线）：  
文档 → 切块（把长文章切成小段） → 向量化（每块文字转成数字向量） → 存入向量数据库    
查询阶段（在线）：  
用户问题 → 向量化（把问题也变成数字） → 在数据库中找最相似的向量 → 取出对应文字 + 用户问题 → 塞进Prompt → 发给 LLM 生成答案 -> 返回给用户
# 余弦相似度
通过计算两个向量夹角的余弦值来衡量其相似程度，重点关注方向而非向量长度，夹角越小，余弦值越接近 1，相似度越高；夹角越大，余弦值越接近 -1
## 优缺点
优点：    
1.不需要重新训练模型   
2.可插入最新知识  
3.可控性强（检索结果可过滤）  

缺点：  
1.检索质量决定生成质量，如果检索结果不相关，生成就会出错，且向量检索受 embedding 精度、召回策略影响  
2.上下文拼接成本高：检索到的多条文档要拼接到 Prompt，占用大量上下文窗口（token），增加推理成本  
3.检索与生成割裂：检索和生成是两个阶段，模型无法在生成过程中动态调整检索策略  
4.知识更新成本：向量数据库更新需要重新生成 embedding，数据量大时成本高
## 升级
### HyDE（Hypothetical Document Embeddings）
1.在检索前，模型先生成一个“假设回答”或“假设文档”，然后用它去检索  
2.这样可以提高检索相关性，因为检索的 query 更接近目标答案的语义
### Multi-hop RAG
1.不是一次性检索，而是生成过程中多次检索，每次根据当前生成内容调整检索策略  
2.适合复杂推理、多步骤任务  
### Agent RAG
1.检索时调用多种外部工具，而不仅限于向量检索  
2.调用检索工具、API、计算器等，动态获取信息
### GraphRAG
1.用知识图谱增强检索  
2.检索时不仅找相似文档，还能沿着知识图谱关系查找相关节点
### Self-RAG
1.生成过程中自我评估并主动检索  
2.模型在生成过程中自我评估答案质量，如果不满意，就主动检索补充信息再生成
# 关键参数
## Temperature
控制输出的"随机性/创造性"，范围通常 0.0 ~ 2.0   
Temperature = 0.0  
输出几乎固定，每次结果相同  
适合：数据提取、格式化输出、代码生成  
示例：从文本中提取日期 → 必须准确，不能乱发挥  
结构化输出任务 → Temperature: 0.0 ~ 0.3  


Temperature = 0.7（默认值）  
平衡创造性和准确性  
适合：通用对话、问答系统  
普通对话助手 → Temperature: 0.5 ~ 0.8  

Temperature = 1.5+  
输出非常随机，充满创意但可能乱说  
适合：创意写作、头脑风暴、生成多样化内容   
创意内容生成 → Temperature: 1.0 ~ 1.5
## Top-P
核采样，控制模型从"概率最高的前X%词"中选择下一个词  
Top-P = 0.1  →  只从概率最高的10%词中选  →  保守、稳定  
Top-P = 0.9  →  从概率最高的90%词中选    →  多样、自然  
Top-P = 1.0  →  从所有词中选             →  完全随机  
## Max Tokens
最大输出长度，限制模型单次输出的最大Token数  
设置太小 → 回答被截断，输出不完整  
设置太大 → 浪费费用，增加延迟  

实用参考：  
├── 简单问答：256 ~ 512  
├── 详细解释：1024 ~ 2048   
├── 长文生成：4096+  
└── 不限制：不设置此参数（按模型上限）
## Stop Sequences
停止词，告诉模型遇到某个字符串就停止输出  
应用场景：  
├── 输出JSON时，遇到 "}" 就停  
├── 输出代码时，遇到特定标记就停  
└── 控制对话轮次
# Fine-tuning vs RAG
## 区别
RAG（检索增强生成）                                                                                           
原理：不改变模型，在推理时动态注入相关知识              
流程：问题 → 检索相关文档 → 塞进Prompt → 模型回答                                                         
类比：开卷考试，考试时可以翻书     
特点：成本低，难度低，可实时更新，准确性高（可溯源），推理推迟高（检索），只需文档  
Fine-tuning（微调）    
原理：用新数据继续训练模型，改变模型参数  
流程：准备数据集 → 训练 → 得到新模型 → 部署  
类比：闭卷考试，知识已经背进脑子里了  
特点：成本高（GPU训练），难度高，更新需要重新训练，准确性低（可能产生幻觉），推理延迟低，需大量标注数据
## 选型决策树
让模型知道最新的/私有的知识（文档、数据库）：RAG  
让模型用特定的语气/风格/格式回答：先试 Prompt Engineering，不够再考虑Fine-tuning  
让模型学会一种新的任务类型（如特定格式的信息抽取）：考虑 Fine-tuning  
知识需要频繁更新（每天/每周）：用 RAG（Fine-tuning更新成本太高）  
需要极低延迟，不能有检索步骤：考虑 Fine-tuning  
# 问题
## 幻觉
模型一本正经地说出不存在的事实，编造不存在的文献、API函数、时间等。  
原因：LLM的目标是"生成看起来合理的下一个词"，而不是只说真是内容。  
### 解决
1.RAG（最有效）：给模型提供真实的参考文档，让它基于文档回答，Prompt中加："只根据以下文档内容回答，文档中没有的信息请说不知道"。  
2.Prompt约束："如果你不确定，请直接说不知道，不要猜测"。  
3.降低Temperature：Temperature越低，模型越保守，越不容易乱说。  
4.输出验证：对关键信息做二次验证（调用工具、查数据库）。  
5.引用溯源：让模型输出时标注信息来源，方便人工核查。
# MCP VS CLI
二者不是同一层级，但经常被拿来做同一件事：让 LLM 调用外部能力
## MCP
Model Context Protocol,不是某个具体工具，而是一套面向模型工具调用的协议层,属于协议层.  
它更关心的是：  
1.工具有哪些能力  
2.参数 schema 怎么定义  
3.client 如何 discover 这些工具  
4.调用结果怎么结构化返回  
5.一个 server 如何被多个 client 复用
## CLI
（Command-Line Interface）非常具体的工具入口，不需要理解太多协议，只需要调用命令、传参数、拿 stdout/stderr、再决定下一步。  
1.真正干活的本来就是CLI  
2.对单机、本地环境来讲，更加灵活（权限和变量已经确认，执行边界依然清晰）  
3.更省token（context更轻，agent聚焦决策，更容易命中缓存）
## Summarize
1.MCP 解决的是“能力标准化暴露”问题：各种约束、统一格式、工具、兼容版本、共享agent，解决是什么、怎么用。  
2.CLI 解决的是追求低token、快速自动化流程：前提是工具本身成熟、无需额外关注权限（单机、本地）  
3.所以应分场景选择，且经常应该组合而非二选一：底层能力 继续由 CLI 实现，对模型暴露层再根据需要包装成 MCP
# Prompt
Prompt要清晰，一个完整的Prompt通常包含：  
角色（Role） - 你是谁  
背景（Context） - 情况是什么  
任务（Task） - 要做什么  
格式（Format） - 输出什么样  
# Temperature
越小越保守，越大越开放，根据场景和业务需求确定
## System Prompt
角色设定，明确职责、制定回答规则，确定边界，要有防御性设计（如回答边界）
# 结构化输出
约束回答格式：markdown、json等，可固定输出格式，例如Open AI的JSON Mode
# Chain of Thought 
思维链，区别于直接回答，可以看到每一步的思考过程  
"让我们一步步思考" 这句话有神奇的效果
## Zero-shot CoT
零样本的思维链，让LLM自己生成思考过程，一般两次提示（生成推理过程 -> 提取具体答案）  
无需示例预训练，直接通过提示词让模型生成推理链，更加灵活开放
## Few-shot
少样本学习，用例子教会AI做特定格式的任务
# Streaming
流式输出，数据生成的同时被逐步发送或处理，而非等待全部生成后一次性输出，让AI应用有更好的用户体验，为后续项目做准备（stream=True流式 + flush=True实时输出）
# Token 用量统计
prompt_tokens（输入） + completion_tokens（输出）
# 错误处理与重试机制
必须有完善的错误处理，例如：触发限流、请求超时、API错误、未知错误等
# LangChain
开源框架，用于构建基于大型语言模型（LLM）的应用程序,提供各种工具，把做AI应用的重复工作都封装好，让你专注业务逻辑，不用重复造轮子、换模型成本低、开箱即用TAG、Memory等。  
例如：Android的Jetpack  
Retrofit 封装网络请求    →      LangChain 封装LLM调用  
Room 管理本地数据库      →      LangChain 管理向量数据库  
Jetpack 提供组件库       →      LangChain 提供AI组件库  
ViewModel 管理状态       →      LangChain 管理对话记忆  
WorkManager 处理任务链   →      LangChain 处理AI任务链  
## 核心模块
1.Models（模型层）：统一封装各家LLM，一套代码换模型。  
2.Document Loaders（文档加载）：PDF、Word、网页、CSV... 一行代码加载。  
3.Text Splitters（文本切块）：各种切割策略，不用自己写。  
4.Embeddings（向量化）：对接各家Embedding模型。  
5.Vector Stores（向量数据库）：Chroma、Milvus、Pinecone... 统一接口。  
6.Chains（任务链）：把多个步骤串联成流水线。  
7.Memory（记忆管理）：自动管理多轮对话历史。  
8.Agents（智能体）：让AI自主决定调用哪些工具。
# Funtion Calling
RAG 是让 AI 查知识库（被动检索，从知识库找现存内容，适合历史数据、文档问答）,Function Calling 是让 AI 调用你写的函数（主动调用，执行函数获取实时数据），例如：  
没有 Function Calling：  
用户：茅台现在多少钱？  
AI：我的训练数据截止到xxx，无法获取实时价格    
有了 Function Calling：  
用户：茅台现在多少钱？  
AI：我需要查一下实时价格  
    → 自动调用 get_stock_price("600519")  
    → 拿到返回值 1440.02  
    → 茅台现在价格是 1440.02 元    
本质是写好工具函数后告诉 AI 有哪些工具、每个工具是干什么的，AI 自己决定什么时候调用哪个工具
# 记忆
## 问题
1.上下文窗口的限制导致遗忘问题：信息超出Context Window，LLM就“忘记”了它，无法再访问，导致所谓的“遗忘”问题。  
2.难以处理多轮/复杂任务：对于需要跨越多轮对话、追踪状态或执行一系列子任务的复杂任务，LLM很难保持连贯性和进展，因为它会不断“忘记”之前的步骤和决策。特别是在Agent的场景，工具的定义和工具的返回值都会存在于上下文中，同时由于Agent具有自主工作的能力，和LLM的平均交互的轮数也大大增加。  
3.无法个性化：由于不记住特定用户的历史偏好、习惯或之前的互动，LLM难以提供真正个性化的体验。每次互动都像是第一次见面。  
4.长上下文带来的性能和成本影响，推理速度变慢：LLM在处理更长的上下文时，需要进行更多的计算来处理和理解所有输入信息，导致推理时间增加，响应速度变慢，模型表现下降：尽管LLM的上下文窗口越来越大，但模型在超长上下文中检索关键信息的能力可能会下降。此外还会有更高的Token费用：上下文越长，输入的token数量就越多，从而导致每次API调用的成本更高，对于需要频繁交互或处理大量文本的应用来说，这会迅速累积成可观的费用。
## 分类
1.短期记忆/工作记忆（Short-term Memory, STM）：Agent维护当前对话和任务的即时上下文系统，主要包括：  
会话缓冲（Context）记忆保留最近对话历史的滚动窗口，确保回答上下文相关性；  
工作记忆：存储当前任务的临时信息，如中间结果、变量值等。  
短期记忆受限于上下文窗口大小，适用于简单对话和单一任务场景。  
2.长期记忆（Long-term Memory, LTM）：是Agent用于跨会话、跨任务长期保存知识的记忆形式。它对应于人类的大脑中持久保存的记忆，例如事实知识、过去经历等。长期记忆的实现通常依赖于外部存储或知识库，包括但不限于：  
摘要记忆：将长对话内容提炼为关键摘要存储；  
结构化知识库：使用数据库或知识图谱存储结构化信息；  
向量化存储：通过向量数据库实现基于语义的记忆检索(传统RAG解决的就是这个问题)。  
长期记忆使Agent能够随着时间累积经验和知识，它特别适用于知识密集型应用和需要长期个性化的场景。  
## 记忆管理
要判断判断哪些信息需要被记忆，包括时间维度、空间维度、参与者状态、意图上下文以及文化上下文等等，具体例如：  
1.代码助手类的Agent：用户项目的上下文和偏好(仓库结构、命名风格、常用框架等)。  
2.智能客服类的Agent：用户历史和偏好（当前任务状态、上次建议等）。  
3.个人助理Agent：用户个人信息和日程表（经常执行的行为模式、制定目标等）。  
4.推荐服务Agent：用户的显式/隐式反馈（点击行为、购买历史、浏览记录等）。
## 记忆策略
1.通过轮数触发：每隔3-5轮对话自动生成摘要存入记忆。  
2.事件触发：在完成任务、场景转换等关键节点记录信息。
## 记忆存储
通常采用用户→会话→记忆片段的三层结构管理。  
1.用户层：分不同账号空间。  
2.会话层：隔离各对话上下文。  
3.记忆片段层：存储具体内容及元数据（如时间、关键词、来源等）。  
复杂系统可能需要维护多个记忆库，包括短期工作记忆、长期情节记忆、语义知识库等。合理的结构设计有助于快速检索和有效管理记忆内容
## 记忆检索
Agent需要基于当前对话意图从记忆库中检索相关信息。主要检索方法包括关键词匹配、向量语义搜索和元数据过滤。  
系统将检索到的记忆按相关度排序，选取最相关内容加入到对话上下文中，用于生成更准确的响应。例如在推荐场景中，可基于用户历史偏好记忆提供个性化建议。
## 记忆框架
### Mem0
#### 结构
1.核心记忆层：构建核心逻辑来判断新增、检索、更新和删除记忆的相应实现。  
2.大语言模型层：负责根据用户输入提取出关键信息，以及生成如何更新记忆的决策。  
3.嵌入模型和向量存储层：负责支持记忆的向量化存储和检索。  
4.图存储层：负责存储抽取出的实体关系，丰富记忆的组织形态。  
5.持久化存储层：负责存储对记忆系统的操作信息。  
#### 核心技术
1.双 LLM 架构：系统通过两次不同的 LLM 调用实现复杂的分工。第一次专注于信息提取，第二次专门处理决策过程，提高准确性并允许专门优化。  
2.上下文感知处理：在现有记忆上下文中分析新数据，确保记忆系统一致性和连贯性，防止碎片化并维护信息间逻辑关系。  
3.智能去重机制：结合向量相似性搜索与LLM判断，防止冗余信息存储，保持记忆质量和系统效率。  
4.冲突解决能力：当出现矛盾信息时，智能确定保留、更新或删除的适当行动，适应用户偏好和环境的动态变化。
### Letta/MemGPT

采用”虚拟内存“的概念来管理Agent的记忆。  
核心创新在于双层记忆架构，包括上下文内记忆（直接存在于模型上下文窗口中的系统指令、可读写记忆块和当前对话）和上下文外记忆（存储历史对话和外部知识的长期存储）。    
当上下文窗口接近填满时，系统会自动将对话历史压缩为递归摘要并存储为记忆块，同时保留原始对话供后续检索，通过工具如core_memory_append、core_memory_replace 和 recall 实现记忆的编辑与检索，从而使 AI 代理能够在长期交互中保持连贯性，真正实现记住过去、学习新知并随时间演化的能力。
### LangMem
1.语义记忆 (Semantic Memory)：存储客观事实、用户偏好和基础知识，作为长期持久化记忆嵌入系统提示中，可通过 Collection 方式保存完整历史信息，或通过 Profile 方式只保留最新状态，为Agent 提供稳定的知识支撑，确保其能够准确理解和回应用户需求。
2.情节记忆（Episodic Memory）：捕捉 Agent 的交互经历，不仅存储对话内容，还包含完整上下文和推理过程，作为短期记忆主要用于构建用户提示词，使 Agent 能够从过往经验中学习，参考成功案例调整响应策略，从而在类似情境中提供更加个性化和有效的解决方案。
3.程序记忆 (Procedural Memory)：专注于”如何做”的实操知识，从初始系统提示开始，通过持续反馈和经验积累不断优化，作为短期记忆帮助 Agent 学习最有效的行为模式，既可用于系统提示也可用于用户提示，使 Agent 能够根据不同情境灵活调整策略，提高解决问题的效率和准确性。
