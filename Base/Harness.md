# Harness Engineer
```
┌─────────────────────────────────────────────────────────┐
│                    Harness Engineering                   │
├─────────────────────────────────────────────────────────┤
│                                                          │
│   🖥️ 环境        📚 知识        ⛓️ 约束        🔄 回路   │
│  Environment   Knowledge    Constraint   Feedback Loop  │
│                                                          │
│  让 Agent 能    关键信息在      架构规则      快速反馈   │
│  独立运行测试   仓库内可查      机械执行       持续改进   │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

目的是让 Agent 能够可靠、可观测、可持续地工作
## 环境
核心问题：Agent 需要什么样的环境才能有效工作  

Harness 理念：  
环境必须是可程序化的（代码化、可重现）  
Agent 必须能自主运行、测试、观察系统  
环境的差异应该被抽象和隔离  

减少输入多样性（降低环境复杂度）：  
```
Harness 中的衰减机制：
├── 编码规范（限制代码风格多样性）
├── 架构约束（限制设计选择多样性）
├── API 契约（限制接口形式多样性）
├── 提交规范（限制提交信息多样性）
└── 审批流程（限制变更路径多样性）
```
## 知识
核心问题：Agent 如何获取做出正确决策所需的上下文  

Harness 理念：  
运行时读不到的知识等于不存在  
关键决策、架构规则、业务逻辑必须在仓库内可检索  
文档不是辅助材料，而是生产系统的一部分   

扩展边界能力：  
```
├── 测试套件（扩展验证能力）
├── 静态分析工具（扩展检测能力）
├── 自动化部署（扩展交付能力）
├── 监控告警（扩展感知能力）
└── MCP 服务器集成（扩展工具调用多样性）
```
## 约束
核心问题：如何防止 Agent 快速产出导致的系统腐化  

Harness 理念：  
用机械化规则替代人工审查（Lint、结构测试、依赖检查）  
架构边界必须是强制性的，而非约定俗成的  
约束应该在最早阶段拦截问题，而非后期修复  
## 回路
核心问题：如何让 Agent 从失败中学习并自我修正  

Harness 理念：  
所有质量工具的输出都应该是结构化、机器可读的  
反馈不是终点，而是下一次迭代的输入  
人类工程师设计反馈机制，Agent 利用反馈自我改进  
## 实践
```
## 目标
在此仓库中完成 [具体目标描述]。

## 成功标准
- [ ] 标准 1（可量化）
- [ ] 标准 2（可验证）
- [ ] 标准 3（可测试）

## 每轮行动
1. **理解当前状态**
   - 读取 README
   - 检查 COMMIT 和 LOGFILE
   - 验证源代码

2. **调查与规划**
   - 分析依赖关系
   - 理解现有代码
   - 制定实施计划

3. **实现**
   - 按规划执行
   - 保持代码质量

4. **测试与验证**
   - 运行完整测试套件
   - 分析失败（如有）
   - 重复直到通过

5. **提交与记录**
   - 清晰的 commit message
   - 记录实现内容和原因
   - 更新进度日志

## 当前状态追踪
- 上次 COMMIT: [自动填充]
- 当前分支: [自动填充]
- 待完成任务: [从日志读取]

## 约束条件
- 不得修改测试来绕过失败
- 必须保持向后兼容性
- 所有更改必须有测试覆盖
```
